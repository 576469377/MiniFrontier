# MF1 执行性能审计（2026-09-10）

MF1 的旧实现存在明显的执行瓶颈，也存在一处单 token KDA 训练梯度缺失问题。本次完成了代码修复、独立数值对照、CUDA 验证和单卡性能测量。结果支持继续开展正式数据上的资源验收；尚不构成正式预训练、学习曲线或对话能力验收。

最新结果：第二轮跨 batch 注意力优化后，单张 RTX 3090 在 **32×512 固定合成文本、20 次预热＋100 次测量**中达到 **8,533.10 CE token/s**。这是保持 228M 架构、MTP 和梯度检查点的执行测量，真实多模态配方仍需独立验收。具体对照见本文末尾的第二轮记录。

[第一轮数值档案](minifrontier1-execution-performance.json)和[第二轮数值档案](minifrontier1-batched-attention.json)保存源码身份、配置、命令参数、逐步耗时、梯度范数、显存、验证结果及校验值。原始样本、权重和机器标识不随档案分发。

## 瓶颈与修复

| 位置 | 检查发现 | 本次处理 |
| --- | --- | --- |
| [CSA](../../minifrontier/models/minifrontier1/csa.py)、[QSA-MLA](../../minifrontier/models/minifrontier1/qsa_mla.py) | 对每个 query 执行 Python 循环、小矩阵乘法和动态索引；MTP 的注意力也受影响 | 按有界 query chunk 合并计算；稀疏支持集仍保留全部被选择的 token |
| CSA 压缩器 | 每个四 token 块分别建索引、门控池化 | 向量化块成员与 overlap 池化，保留 segment／媒体边界和短块完成时刻 |
| [KDA](../../minifrontier/models/minifrontier1/kda.py) | 独立样本被拆成多个 B=1 调用 | 将等长独立片段合批执行；卷积与递归状态在 packed 边界重置 |
| [LatentMoE](../../minifrontier/models/minifrontier1/moe.py) | 每个专家单独查找 token 并执行小 GEMM | CUDA 使用已有的分组投影工具；保留路由、加权顺序和 FP32 聚合，偏载时回退，不丢 token |
| [训练循环](../../minifrontier/training/minifrontier1.py) | `input_batch_tokens` 只扩大逐样本累积窗口，没有真实的行合批 | 新增 `--batch-size`，默认最多 8 行；先固定全局样本窗口，再按行数和 padding 后 token 容量合批 |
| 梯度检查点 | 每层将 query 计数转成 GPU tensor 后再读回 CPU | 直接返回整数，去掉这次往返 |

128-token 基线更新的 profiler 记录了 31,643 次 `aten::copy_`、6,269 次 `aten::bmm` 和 2,273 次 `aten::nonzero`。执行优化版本的复制调用降至 9,848 次，`nonzero` 降至 649 次。原始前 30 项算子表保存在数值档案中；这些调用包括前向、反向、重计算和优化器，不能用 profiler 的 CPU／CUDA 时间总和直接推算 GPU 利用率。

数据读取也做了独立检查：相同前两个采样窗口的记录校验、tokenization 和媒体预处理，在文件系统缓存已热的情况下分别耗时约 0.041 秒、0.008 秒。本组小数据的每步几十秒耗时主要来自模型执行；该测量不包含 H2D，也不代表大规模媒体数据的冷读性能。

## 正确性问题

旧 KDA 适配器会让单 token 训练片段进入只有前向计算的 FLA recurrent 路径。CUDA 复现中，`q_proj`、`k_proj`、`v_proj`、`b_proj` 的梯度均为 `None`。现在只在无梯度的单 token 推理中使用该路径，训练使用支持反向传播的 chunk 路径。回归要求上述投影梯度存在、有限且非零。影响条件是单 token 片段；不能据此推断所有历史训练都没有 KDA 梯度。

合批引入的两个边界也已修正：

- 索引器均匀教师采样只计算有效 query，增加右侧 padding 不改变原样本的采样位置。
- padding 不参与专家计算，未接收有效 token 的专家继续保持 `grad=None`。这会影响 AdamW 的权重衰减和状态更新，不能用零梯度替代。

合批不改变已选样本窗口、CE／MTP 分母、媒体位置和曝光数。P2 仍按原始 packed 行预先选择注意力阶段，只合并阶段相同的相邻行。路由均衡统计继续排除 padding，并排除梯度重计算产生的重复统计。

## 单卡测量

配置均为 [228M 原生配置](../../configs/minifrontier1/model_228m_native.json)，共 228,235,809 个参数，启用 BF16、梯度检查点、AdamW、路由均衡和 MTP（系数 0.1），使用 RTX 3090 24 GiB，每张物理 GPU 只运行一个项目任务。软件为 PyTorch 2.13.0+cu130、CUDA 13.0，CPU 线程数为 2。其他 GPU 可运行独立任务，未把整台主机视为独占机器。

| 固定输入的合成文本短测 | 基线 CE token/s | 执行优化 CE token/s | 比值 |
| --- | ---: | ---: | ---: |
| 1×128 | 31.54 | 108.63 | 3.44× |
| 1×512 | 60.50 | 527.02 | 8.71× |

每行前后使用同一张物理卡、相同 seed 和 token 预算。只运行了 2 次预热、4 次更新；128-token 的 profiler 更新从吞吐计算中排除。这两行用于定位代码开销，不能作为正式长期吞吐承诺。

最终版本另外完成 **20 次预热＋100 次无 profiler 更新**：8×512、每次更新 4,096 输入 token／4,088 CE token，测得 **1,960.91 CE token/s**，显存预留峰值 **6.71 GiB**。该结果包含前向、MTP、反向、梯度裁剪、AdamW 和路由均衡；不包含数据准备、评估与保存。它是随机合成文本的持续测量，不能与上表不同全局预算直接计算加速比，也不能替代原生多模态阶段验收。

真实数据对照复用了[已有指令诊断数据及重建说明](../experiments/mf1-language-performance-v1/README.md)，使用同一初始化检查点、seed=42、语言／图像／视频 CE 混合权重 0.90／0.075／0.025，均执行 2 次更新。下表取第二步，避免将首次执行开销混入比较：

| 运行 | 最大行数 | 实际微批次数 | 第二步耗时 | 输入 token/s | CE token/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基线 | 1 | 28 | 49.98 秒 | 10.36 | 1.86 |
| 执行优化 | 1 | 28 | 21.48 秒 | 24.11 | 4.33 |
| 执行优化＋合批 | 8 | 4 | 6.00 秒 | 86.28 | 15.49 |
| 最终修复复测 | 8 | 4 | 5.43 秒 | 95.44 | 17.13 |

前三行在同一物理卡执行，第二步约加速 8.3 倍；最后一行在另一张同型号卡上复测，因此不将它相对第三行的差异归因于代码改动。每步 28 条样本的合批形状为 8／8／8／4，第二步包含 518 输入 token、93 CE token。

四个运行结束后的采样器状态 SHA256 和完整 token 账本一致：共 1,037 输入 token、192 CE token、80 MTP target、81 视觉 token、7 次媒体曝光。数值档案保留两步指标和完整验证结果。BF16 合批会改变矩阵乘法的舍入，路由边界也可能随之改变；没有宣称权重或学习曲线逐位相同。真实数据只运行了两步，所有产物都仍是 `budget_complete_unqualified`。

## 回归与后续边界

- 全仓 CPU：349 项通过、1 项跳过；跳过原因是 Qwen 未声明原生 MX QAT 配方。
- 新增 CUDA：8 项通过，包含 KDA 单 token 梯度、BF16 QSA／专家前向及梯度对照，以及图像／视频在 dense 和 sparse 路径的缓存续算、回滚。
- CPU 独立 oracle 覆盖 overlap 池化、逐 query 注意力、packed KDA 输出／梯度／状态，以及 padding、CE、MTP、索引器归一化和未激活专家的 AdamW 更新。
- CUDA 注意力与专家梯度对照满足相对 L2 误差小于 3%、余弦相似度大于 0.999；CPU 浮点对照采用更严格容差。具体断言见 [执行回归](../../tests/test_mf1_execution.py)。
- Ruff、格式检查、Mypy 通过；上游源码映射的 24 个文件校验值全部匹配。

第一轮结束时，注意力仍有按行循环和有界支持集构造，KDA 对不等长 packed 片段仍需分组，路由统计和优化器仍有小算子开销。随后第二轮处理了 dense 注意力与 KDA 合批。旧 `RecordDataset` 会重复校验和编码；正式数据的紧凑加载器及其启动、重开成本见本文最后一节。

本次没有证明 batch=8 最优，也没有依据将其他模型的 batch=128 直接复制到 MF1。后续应在准备好的正式数据、实际 context／媒体预算和既定全局 token 预算下，完成一次有界资源验收，再进入阶段训练；保留既有的能力和数据准入门槛。

第一轮四组真实数据对照已接入本地 TensorBoard 的 `mf1-execution/`，使用统一的 `train`／`perf` 标签；最终验证指标保留在报告中。数值档案可直接重画每步曲线。三个中间诊断检查点在完成采样器／账本比对并记录校验值后已回收，释放约 12.75 GiB；当时保留该轮最终检查点及共享初始化权重。

## 第二轮：跨 batch 注意力与 KDA 片段合批

第一轮解决了逐 token 调度，但 dense 注意力仍逐样本执行，增大 batch 没有充分合并计算。8×512 的新剖析记录了 62,918 次 `cudaLaunchKernel`。CSA 和 QSA-MLA 的前向及重计算 CPU 总时间分别约 754 ms、833 ms，占该次 profiler CPU 总时间约 46%；这不是整步 GPU FLOPs 的比例。

本轮将无需缓存的 dense CSA、QSA-MLA 和 MTP 注意力改成跨 batch 计算，使用 [PyTorch SDPA](https://docs.pytorch.org/tutorials/intermediate/scaled_dot_product_attention_tutorial.html)。CSA 保留有界 query mask 和压缩块的完成时刻；MLA 保留原生投影、mRoPE、门控和尺度。块目录只构造一次，供多层及梯度重计算共用。缓存推理、索引器蒸馏及 sparse 主注意力继续使用已有校验路径。

KDA 的无缓存执行按长度区间合并独立片段，组内补齐后的 token 位置数小于有效位置数的两倍，取回有效位置；卷积与递归状态不跨 segment。完整、无 padding 的行直接批量执行。训练不再生成随后被丢弃的末端推理状态。没有减少层数、参数、MTP 或训练 token。

修改后同一配置的 profiler 中，CSA 和 QSA-MLA 对应 CPU 总时间降至约 43 ms、19 ms，`cudaLaunchKernel` 次数降至 21,332。重算后的主要开销转向专家计算、KDA、输出头和其他残差／路由操作。

### 相同全局预算的对照

以下三项在同一张物理 RTX 3090 上顺序执行，固定 seed=42、长度 512、每步 **16,384 输入 token／16,352 CE token**。输入是固定随机 token 窗口，每次更新重复使用，用于测量执行性能。每项 3 次预热＋8 次测量，包含梯度累积、裁剪、AdamW 和路由均衡。

| 版本 | microbatch | 累积次数 | CE token/s | 峰值 reserved GiB |
| --- | ---: | ---: | ---: | ---: |
| 第一轮边界修复 | 8 | 4 | 2,002.77 | 6.71 |
| 第二轮执行优化 | 8 | 4 | 6,012.08 | 6.85 |
| 第二轮执行优化 | 32 | 1 | 7,958.33 | 20.15 |

相同 microbatch 的代码提速约 **3.00 倍**；再把相同全局窗口由四次微批合为一次，短窗口达到基线约 **3.97 倍**。首次更新梯度范数分别为 0.832850、0.832738、0.831699；不能据此推断长期学习曲线完全相同。

随后只对 microbatch=32 完成 **20＋100** 持续测量：测量段处理 1,635,200 CE token，耗时 191.63 秒，平均 **8,533.10 CE token/s**，峰值 allocated **10.21 GiB**、reserved **20.91 GiB**。这证明该文本执行配置可达到约 8K TPS；它仍不包含数据加载、评估、保存和生产媒体解码，也不代表长上下文或视觉阶段有相同速度。

同一张卡上的真实混合诊断数据复测使用与第一轮相同的初始化、样本流、global input=512 和 microbatch=8。第二步耗时 **5.43→2.73 秒**，CE 吞吐 **17.13→34.09 token/s**。两步累计采样器状态校验值、CE／MTP／媒体账本、参数名称和形状完全一致。短诊断样本具有大量非监督输入，不能把此结果与合成文本的 8K TPS 混为一个指标。

### 数值、回归与保留策略

无缓存 dense 路径新增了 CPU／CUDA 的 packed、媒体边界和 padding 对照。CPU 使用严格 FP32 输出及梯度容差；CUDA 检查输出和梯度向量误差。SDPA 与手写 BF16 运算的舍入不同，额外以全 FP32 注意力为 oracle 复核：新版 CSA／QSA 参数梯度相对 L2 误差分别约 **0.61%／0.66%**，输入梯度约 **0.65%／0.72%**，该探测中均未高于旧 BF16 路径的对应误差。完整数值含最大绝对误差和余弦相似度，保存在第二轮档案。

冻结提交 `5871666` 的全仓 CPU 回归为 **352 passed、1 skipped**；CUDA 执行回归为 **11 passed**。Ruff、格式和 Mypy 通过。一次可变主目录的恢复测试遇到 recipe 身份不一致，当时主目录配置正在并行变更；完整回归改在冻结源码上通过，恢复身份检查保持原样。

训练入口默认 microbatch 仍为 8。32 是 **512-token 文本的执行候选**，不能直接套用到更长上下文或较重媒体预算。生产验收仍须使用实际阶段数据、长度和媒体配置。本轮全部测量结束，未自动重启旧的小 batch 学习实验。

TensorBoard 的 `mf1-execution/batched-*` 提供三项受控短测、持续测量和真实数据复测；合成曲线由完成后的逐步报告重建，横轴应使用 step。旧审计保留检查点已记录校验值后由本轮检查点替代，释放约 4.25 GiB；共享初始化权重保留，源码和数值档案不包含权重。

## 大数据加载与吞吐指标

正式数据准备期间接入了 [MF1 紧凑二进制加载器](../../minifrontier/data/minifrontier1_encoding.py)，保存 token、监督位图和稀疏媒体信息，避免逐次重新分词。进一步检查发现，该加载器最初把完整文件校验放在四分片 LRU 的打开函数中。随机采样超过四个分片后，每次重开可能重新扫描整个分片；默认 64M token 的 uint16 IDs 与 mask 合计约 129.7 MiB，还不包括索引和媒体描述。这是大数据路径中的额外 I/O 风险，不能用它解释之前使用旧 JSONL 的慢速诊断结果。

现已分别缓存至多四组数据映射和四个小索引映射。采样器的长度、领域初始化只读取索引；数据文件首次打开校验 SHA256，重开时核对设备、inode、长度、mtime 与 ctime，文件身份变化后重新完整校验。媒体描述也用 memmap 按偏移读取，避免每条样本反复打开文件。原始媒体哈希与解码校验保留，不缓存可训练视觉塔的输出。

[回归测试](../../tests/test_mf1_compact_data.py)覆盖超过四个分片的反复访问：未变化的每个文件只完整校验一次；修改 token、索引或媒体描述后，即使恢复 mtime，重开仍拒绝。文本、图像、视频的输入、监督位置和模型输出保持一致，暂停恢复的模型、优化器、采样器、路由与 RNG 逐值一致。相关加载、工作流与指标测试共 34 项通过。

训练循环还把每个微批的 CE 计数放在已有 CPU labels 上，减少一次 CUDA 标量读取。新运行在既有 `perf/` 分组增加：

- `data_preparation_seconds`：更新前的读取、媒体准备、packing 与 CE/MTP 分母准备耗时；不含 H2D、模型执行、验证和保存。
- `ce_fraction`：有效主 CE / 非 padding input token；indexer 阶段为零。
- `padding_fraction`：合批补齐位置 / 实际送入模型的全部位置。

全仓 CPU 回归为 **370 passed / 1 skipped**，52 项 CUDA 测试未在这轮数据路径回归中运行；Ruff、格式检查和 173 个源文件的 mypy 通过。这些指标与 `input_per_second`、`ce_per_second` 一起解释吞吐差异。新加载器尚未完成正式多模态数据上的 GPU 性能验收，本节不追加 TPS 或端到端加速比；上文 8,533 CE token/s 的测量范围保持不变。
