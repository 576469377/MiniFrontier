# 训练执行优化（2026-09-11）

2026-09-11 的执行优化降低了数据等待与 Qwen 优化器开销，并修复 Kimi 恢复后的闲置显存占用。正式任务从原检查点接续，模型结构、样本窗口、学习率和损失分母保持；数值差异与源码切换依据见下文。当前训练安排见[预训练计划](../pretraining-plan.md)。

## 数据通路

- `MINIFRONTIER_PREFETCH_WINDOWS=1` 启用一个 CPU 后台线程，最多提前准备一个训练窗口。默认关闭。
- 生产线程独占训练数据集与采样器，使用采样器自身 RNG；检查点仅保存已消费窗口的采样状态。预取但未消费的内容在恢复后重新准备。
- 原生模型入口仅支持单卡、固定 input-token 目标、sample-bounded 的预训练。MF1 限于采样随机数完全由生产线程管理的 pilot/P0/P1/P3；P2 不启用此路径。
- 媒体缓存按固定数量的锁条带协调下载，同一文件合并请求；远端下载不再持有整个缓存的排他锁。原始字节 SHA256、缓存容量、验证图片 pin 和磁盘预留仍保留。
- Python 未暴露 `os.memfd_create` 时尝试 libc 接口，为原处理器提供相同字节的匿名内存文件；系统不支持时仍回退到有界临时文件。

预取将原始数据准备与模型计算重叠，视觉编码器仍逐步训练。共享磁盘预留锁保留，检查点写入仍可能使其他任务等待。

## Qwen 优化器

同形状的语义矩阵块最多 32 个合批执行 Polar Express。每个矩阵独立做 Frobenius 归一化，仍使用原来的 FP32、8 轮系数、epsilon、动量、缩放和权重衰减。混合 Q/gate 中的 AdamW 行及 n-gram 表的衰减规则不变；检查点中的参数组与状态布局不变。

在单张 RTX 3090 上，以 513,405,536 参数配置的同一份正式检查点及同一组固定梯度，分别执行旧、新优化器各 3 次更新。第 1 次用于稳定执行，第 2—3 次取平均；没有增加正式训练 token。

| 项目 | 逐矩阵执行 | 同形状合批 |
| --- | ---: | ---: |
| 优化器平均耗时 | 3.664 秒 | 0.498 秒 |
| 峰值 allocated 显存 | 6.806 GiB | 6.804 GiB |

[逐次数值记录](training-infrastructure.json)包含梯度 seed、配置校验值和源码版本。优化器部分约快 7.36 倍。3 次更新后的参数最大绝对差异为 `4.47e-8`，相对实际参数更新的 L2 误差为 `3.12e-6`；优化器动量及 Adam 状态逐值一致。矩阵合批改变浮点舍入，因此结果按容差比较。

## 验证与恢复

针对优化器、缓存并发/损坏/容量、预取、训练运行时和初始阶段绑定的 CPU 检查共 27 项通过；另有 2 项启用预取的规范文本/图文恢复检查通过。MF1 的串行、预取和暂停恢复对照保持模型、优化器、路由、采样器、token 台账与 RNG 逐值一致。

源码切换需要显式的 `execution_only_resume` 记录，绑定原检查点 SHA256、新旧源码身份、阶段证据和验证记录。恢复比较仍拒绝 batch、数据、模型配置、优化器、预算或阶段变化。原检查点和原运行证据保留，后续日志使用新源码身份。

本轮单卡任务支持在输出目录创建 `pause.request`，于当前优化器更新完成后保存并暂停。

## 正式接续后的观察

三个任务接续后的早期记录如下。各行来自实际混合数据，批次与观测窗口不同。

| 模型 | 观测训练步 | 已记录步数 | CE token/s | 前台数据等待 |
| --- | --- | ---: | ---: | ---: |
| Kimi | 405–430 | 6（每 5 步记录） | 约 3,756 | 约 0.006 秒/步 |
| Qwen | 305–365 | 13（每 5 步记录） | 约 1,456 | 约 0.002 秒/步 |
| MF1 | 652–671 | 20 | 约 1,807 | 约 0.035 秒/步 |

启用预取后，`data_preparation_seconds` 表示前台等待数据及尚未前移的元数据准备，不再包含与 GPU 计算重叠的全部后台准备时间。应结合完整更新耗时判断预取收益。[数值档案](training-infrastructure.json)保留逐条记录、seed、配置/数据/tokenizer 校验值与实际源码版本。

Kimi 两次在恢复后的第 401、402 步触发 2 GiB 空闲显存保护，完成的更新均先保存了检查点。仅设置分配器自动回收阈值没有解决；后续版本在验证结束以及必要的预留检查前显式释放闲置 CUDA 缓存，恢复后已继续更新。该操作只回收闲置缓存，见 [PyTorch 内存管理说明](https://docs.pytorch.org/docs/2.14/notes/cuda.html#memory-management)。microbatch、全局 batch、计算公式与 2 GiB 预留均保持原值，峰值计数继续保留。Qwen/MF1 使用 `9b1d8fd`，Kimi 使用包含此修正的 `4ba8955`。

## TensorBoard 展示

四个模型共用 `train / eval / perf` 分类。`train` 展示训练损失、梯度、学习率与进度；`eval` 保留总体验证损失、分域损失和对应 token 分母，阶段末验证使用 `phase_end_` 前缀；`perf` 展示吞吐、步耗时、数据等待、优化器耗时和显存。各训练器已有的吞吐名称保留，因为不同训练阶段的计数分母可能不同；显存统一使用 GiB。

启动、QK 裁剪和缓存回收等运行事件完整保留在 `metrics.jsonl`，不再将这些事件附带的累计 token 数重复画成学习曲线。旧版 Kimi 的 `qk_clip/main_ce_tokens` 只是累计计数，不是 QK 裁剪幅度；逐层诊断一直保存在 JSONL 的 `layers` 中。预训练验证中的 reward 占位值、布尔状态也不再生成图表。

展示服务使用 [展示同步脚本](../../scripts/sync_mf1_tensorboard.py) 从原日志构建独立 event 目录，并保留原 step 和 wall time，再切换 TensorBoard 展示目录。脚本名称为兼容已有服务保留，现支持全部训练器；`--watch --event-driven` 在 Linux 上由文件写入事件唤醒，`--interval` 控制更新合并间隔。源日志目录需已存在，每次启动使用新的展示目录。源日志被替换或截断时明确报错，需在新目录重建视图。

5 项 CPU 展示检查通过，覆盖分类、原生与 MF1 分域指标、原始时间戳、半行写入、增量同步及展示链接保护。本次只更换展示服务，正式训练进程未重启。
