## 本轮核对修正

| 原先的问题 | 修正及对已有结果的处理 |
| --- | --- |
| microbatch 越大越快，便直接选择长期配方 | 取消吞吐选择器自动派发超过 1M CE 的训练；先控制全局 batch，再联合比较 LR、质量与 GPU 小时 |
| `input_batch_tokens=16384` 被读成实际固定 16K | 旧训练器以整个 microbatch 越过目标；保留原始数据并标记差异。新训练器按完整样本控制窗口，超出量小于每 rank 一个最大长度样本 |
| 三个来源模型共同采用 WSD/400K warmup，被误读为官方配方 | 明确这只是旧版共同对照；Kimi 的报告基线改为 cosine/1% LR warmup，Qwen 固定全局 batch，DeepSeek 比较 batch ramp |
| 单因素较优的 LR 与 MTP 直接组合，或只补新 seed | 新组合先做相同 seed 的联合对照；只对入选配方补 seed。旧 seed 试验停止后不计作完成 |
| MF1 训练题答对就扩大指令诊断 | 30K 控制保留为协议/记忆证据。约 2 CE/s 的两项 100K 扩展已停止复核，先解决执行性能 |
| MF1 两组扩展被视为同初始化 LR 对照 | 两组继承各自不同 LR 的控制检查点；属于两条完整路径的比较，不能独立归因于扩展阶段 LR |
| MF1 检查点写 `paused`，监督器恢复后台账仍显示暂停 | 台账读取监督器和最新训练日志；保存点、已观察进度、执行状态分开 |
| DeepSeek 命令里的 `--muon-lr 0.01` 被当作生效值 | 源码核对发现 DeepSeek 的 Muon/AdamW 都使用 `--lr`；该路由不使用 `--muon-lr`。旧 reference 实际两者均为 3e-4，低 LR 对照均为 1e-4。新记录显示有效 Muon LR，不改动旧运行 |
| 目录里的阶段、父扫描、安装测试都被算成实验数 | 每项有稳定 ID、父子关系、用途及解释限制；台账记录数不等于科学试验数或 GPU 作业数 |

## 报告依据与本地选择

| 路线 | 上游明确披露的内容 | 本项目如何使用 |
| --- | --- | --- |
| MiniKimi-K3 | 独立调优各 schedule 的 batch/LR；cosine、1% 线性 LR warmup、WD 0.1。没有在该配方章节披露完整 batch ramp | 比较固定 16K/32K/64K input batch，并为各档分别调 LR；不宣称复制了未公开的增长节点。[Kimi §3.2–3.3](https://arxiv.org/html/2607.24653v1#S3) |
| MiniQwen4 | 新架构/Muon 的实验中 batch warmup 未改善最终结果，增加更新次数，正式配方选择固定全局 batch | 默认不加入 batch warmup；保留 LR warmup。旗舰 25.2M global tokens 不能直接搬到当前小模型。[Qwen §3.2](https://arxiv.org/html/2608.30320v1#S3) |
| MiniDeepSeek-V4 | Flash 的全局 batch 从小值增到 75.5M tokens；先 LR warmup，再平台及末段 cosine。起始 batch 和完整增长节点未披露 | 比较固定 16K、固定 32K 与 8K→16K→32K；本地节点、LR 和预算均标为候选值。[DeepSeek §4.2.2](https://arxiv.org/html/2606.19348v1#S4) |
| MF1 | 没有这个融合模型的官方技术报告 | 分别核对借用原语的来源，再验证组合；不把任一上游的最优超参数称为 MF1 最优 |

补充调研：[AI2 的 critical batch 研究](https://arxiv.org/html/2505.23971v1)用检查点分支训练直接测量 batch 增大后的损失恢复，说明吞吐与 token 效率需要共同考虑。其 OLMo 结果不能覆盖 Qwen 的架构/Muon 实验，因此 MF1 的 batch 增长也应作为候选，而非普遍规则。分支若改变 batch/配方，应保留父权重、优化器是否继承及数据位置的记录；当前 `--resume` 仍只允许配方完全一致，不能用 `--init` 重置 moments 后声称精确继承。

## batch 128 的实际含义

以下是同一冻结来源、相同 seed、相应真实语料上的约 1M CE **短测**。性能均为 3 次预热后 8 次更新；验证使用固定抽样 32 例，表中为终点 LM NLL。数据来自[本轮数值档案](2026-09-10-batch-frontier/README.md)。

| 主机 / 模型 | microbatch | CE token/s | 平均 input / update | 约 1M CE 的更新数 | peak reserved GiB | 终点验证 NLL |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 远端 / Kimi | 16 | 3,223 | 18,717 | 54 | 5.41 | 8.0135 |
| 远端 / Kimi | 32 | 4,446 | 23,767 | 42 | 7.37 | 8.2245 |
| 远端 / Kimi | 128 | 8,053 | 48,158 | 21 | 19.18 | 9.0761 |
| 本机 / Kimi | 128 | 8,295 | 48,158 | 21 | 19.80 | 9.0976 |
| 远端 / DeepSeek | 16 | 2,995 | 18,219 | 54 | 11.54 | 8.1951 |
| 远端 / DeepSeek | 32 | 4,517 | 22,955 | 42 | 19.37 | 8.4448 |
| 远端 / Qwen | 16 | 1,079 | 18,218 | 56 | 9.86 | 8.1735 |
| 远端 / Qwen | 32 | 1,489 | 22,913 | 43 | 12.69 | 8.6369 |

**128 是 Kimi/512 长度/当前媒体比例下很有价值的执行候选。** 相比远端 16 档，实测 CE/s 约 2.50 倍，且约 19–20 GiB reserved 留有一定空间；这不是固定全局 batch 的纯加速比。每百万 CE 更新数减少约 61%，累积窗口也明显增大。每次更新约 5.9 秒，优化器约 0.3 秒，说明不只是省去 optimizer，较大的前后向也减少了很多微批调用开销。

`128 × 512 = 65,536` 是填充后的输入位置上限。这批真实样本平均有效长度更短，所以每次约 48K 非 padding input，不能将 batch 128 直接等同固定 64K，也不能把 input 与 CE 混用。吞吐不含完整验证、保存和整个进程的启动开销；最终要另报完整作业的 GPU 小时/百万 CE。

这次较大 batch 的短测 NLL 更高，是需要继续验证的信号。实验只有一个 seed、小验证子集，且各档没有独立调优 LR；1M 短测沿用的 400K warmup 占到自身预算 40%，区别于 20M 试验的 2%。因此既不能断言 128 长程一定更差，也不能仅因利用率高就确定从第一个 update 使用它。

在声明的 21 GiB allocator 限制下，Qwen 128 和 DeepSeek 64 已触及 OOM 边界；不是所有模型都能使用 128，也不代表在任意实现/长度下硬件绝对无法运行。MF1 的 8/16 档仍约 68 CE/s，其 trainer 目前按样本/packing 累积，没有直接使用 benchmark microbatch 的训练入口；不能将 Kimi 的结论移植过去。

### 修正后的执行控制

三个来源模型的 `--batch-size` 是单卡每次前后向的**样本上限**；`--input-batch-tokens` 是全局非 padding input 目标。默认 `sample-bounded` 策略在窗口末尾减小微批；不截断媒体或标签，不丢掉样本。目标小于大微批容量时不会硬塞 128 个样本。

实现先选定整个更新窗口的样本，再按 microbatch 上限合批，末尾只保留一个不满批次。首次保守实现把取样时的多个小尾批直接送入前后向，固定 64K 时 128 档仅约 4,348 CE/s、16 档约 2,855；这暴露了调度开销。

后续合批实现已经完成真实数据复验：**128 档 6,772 CE/s、19.17 GiB；16 档 3,523 CE/s、5.29 GiB**，约 1.92 倍。两组消费完全相同的 1,045,978 CE、1,052,262 input，均为 16 次更新，终点小验证集 NLL 分别 9.47726/9.47779。两次实现的来源和曲线分别保留在[受控结果](2026-09-10-batch-frontier/controlled-batch-comparison.json)。这项对照使用同机两张 3090，尚未交叉换卡，也未完成 50+200 的完整性能准入。

```bash
# 以下是附加到完整 train 命令的参数，不是独立启动命令。
# 固定全局 64K，对照 microbatch 上限 16 与 128：
--batch-size 128 --input-batch-tokens 65536 --input-batch-policy sample-bounded

# DeepSeek 本地 batch ramp 候选，以已消费的 CE 为节点：
--batch-size 32 --input-batch-tokens 8192 \
  --input-batch-schedule 0:8192,400000:16384,2000000:32768
```

第二个示例中的 0.4M/2M 节点适用于待测 20M CE 候选，是本项目选择；不是 DeepSeek 官方未披露的超参数。LR warmup 另由 `--warmup-tokens` 控制。日志与 TensorBoard 分别记录目标 input、实际 input、实际最大 microbatch、CE 账本和 LR。改变策略必须新建运行目录；旧冻结源码仍保留原行为。

## 试验顺序与停止条件

候选表不是一次性全排列派发清单。先完成正确性和每组最多 1M CE 的排错/性能检查，再投入 20M；不以 1M 小验证集对接近候选做最终排名。首轮使用 seed 42，第二轮只给最有希望的两个配方补 43/44。正式数据、词表和足够预算之前不冻结最终选择。

| 优先级 | 试验 | 固定项和比较变量 | 进入下一步需要什么 |
| --- | --- | --- | --- |
| P0 | 实际全局 batch 控制 | 同版本、同数据流、同目标 input；改 microbatch ceiling | 相同更新窗口、CE 归一化、恢复和 DDP 分片检查；真实 CUDA 短测 |
| P0 | MF1 等价执行优化 | 保留原模型/参数/数据/损失；改算子与调度 | 前后向、因果/媒体边界、缓存与回滚等价；真实图文/视频性能 |
| P1 | Kimi 固定 batch × LR | 16K/32K/64K；cosine + 1% LR warmup；各档 Muon LR 0.003/0.005/0.01 候选 | 20M 同 CE 的 NLL、领域表现、稳定性与 GPU 小时；与旧 WSD 结果分开 |
| P1 | Qwen 固定 batch × LR | 16K/32K，Muon LR 0.003/0.01；其余同候选 | 不默认加 batch ramp；不同 schedule 若比较，须各自调 LR |
| P1 | DeepSeek batch ramp | 固定 16K/32K 对比 8K→16K→32K；先固定 LR，再给各策略同等 LR 搜索机会 | 控制实际窗口；20M、稳定性、损失和成本共同选择 |
| P1 | 数据与 tokenizer | 固定留出文档；32K/64K 的切分、byte-NLL、成本 | 独立来源/许可、近重复、污染、媒体曝光及重建核对 |
| P2 | 联合配方与补 seed | 只改变已登记的一组组合；同预算 | 至少第二 seed，保留失败结果和不确定性 |

NaN、梯度异常或硬件/磁盘越界立即停止自己的任务并保留可用检查点。质量淘汰基于同 CE 检查点和预先固定的验证规则；不能因为某几步下降慢就临时换数据或改变预算。21 GiB/2 GiB 是本轮 3090 性能筛选的限制，最终阶段仍需 50 次预热 + 200 次测量及实际模态准入。

## MF 系列：组合的合理性必须单独验证

MF1 借用 KDA、压缩历史、索引读取、GR、LatentMoE 与浅层查表。单个模块在旗舰规模有效，并不能证明它们在 228M、16 层、当前数据量下互补。本项目保留一条可理解的默认组合，实验负责决定是否删减或替换。

[Engram](https://arxiv.org/html/2601.07372v1)支持研究条件查表这个方向，不证明 MF1 的 8.8M 查表预算已经合适。[SmolLM3 的公开配方](https://huggingface.co/blog/smollm3)展示了用相同模型和预算验证架构/数据变更的方法，适合作为实验方法参考；其数值不能直接套给新 MoE 多模态模型。[SmolVLM-256M](https://huggingface.co/HuggingFaceTB/SmolVLM-256M-Instruct)使用已有语言和视觉底座，其训练成本不能当作 MF1 全随机初始化的预算依据。

| 层次 | 比较内容 | 当前落实状态 |
| --- | --- | --- |
| 必须有的简单基线 B0 | 参数近似匹配的 dense MLA + dense FFN | 当前 schema 限制注意力种类和四流 GR；需实现并验证匹配基线，不能用另一个尺寸的模型代替 |
| 首批机制对照 | B3 lookup 开/关及重分配参数；B9 MTP 0/0.1；B2 合格 indexer 后 dense/full-budget 与 sparse | lookup/MTP 开关已有，匹配配置、索引资格和实验数据仍需单独准备 |
| 后续单因素对照 | B1 CSA 替换、B4 latent/full-width MoE、B5 普通 residual、B6 AttnRes/mHC 替换、B7 稀疏/媒体保护、B8 视觉初始化 | 未完成的适配明确等待实现，不把列出的名称写成已能启动的配置 |
| 配方对照 | AdamW 与适配 Muon；WSD 与 cosine；16K/32K 固定 batch，必要时加入 ramp | 先固定一个结构，对每种 optimizer/schedule 独立调 LR，不同时改架构与数据 |
| 扩大预算 | 正确性/2M → 关键 20M → 前 2–3 个 200M，并补第二 seed | 原方案的阶段预算不变；当前 candidate 数据和 2M acceptance 上限不绕过 |

每项至少报告主 CE、实际 input、媒体次数、总/激活参数和 GPU 小时。报告采用的匹配口径：等 CE、近似等参数或等计算；MoE 总参数相同并不意味着计算相同。重点观察留出文本、EOS、OCR/VQA、图像错配/置黑、视频时间顺序、长距离查找、专家覆盖以及模块/梯度 RMS。32K 与 64K 词表采用固定原文的 byte 归一化评价，不能直接比较 token NLL。

3B 主预训练、120M SFT、正式 RL/教师/OPD/draft/QAT 保留在[原始方案](../training-strategies/2026-09-09/04-MiniFrontier1.0-原生多模态融合架构与全流程实现方案.md)和阶段配置中。当前优先把性能、简单基线、数据和最少必要的消融做实，不再增加无验证依据的组件或并发长训。

## 两台机器如何使用

每张可用物理卡最多一个项目 GPU 作业；本机 GPU 6 仍扣除用户确认的残留显存占用，GPU 7 不纳入本轮池。远端仅使用已确认空闲并通过实际进程/显存检查的卡。空闲卡可执行已经就绪的独立排错、评估或短测；依赖未满足时明确等待，不靠重复启动低价值长训填满卡。

已有三项 batch16 及四项远端大 batch 20M 运行保留为旧版本探索证据；远端吞吐选择长期队列已暂停后续派发。七项 microbatch2 旧任务已停止，两项 MF1 慢速指令扩展另记录为 `stopped_for_review`。完成测量后释放设备，待新计划通过前置条件再启动。资源分配和进程标识仅保存在本地台账，公开资料只用主机标签和相对路径。

磁盘统一保留至少 50 GiB，启动还预留原子 checkpoint 写入空间。短测仅清理其新建目录中明确声明为临时的权重，先保存 hash/大小和数值曲线；代表性和可恢复检查点按[产物规则](../operations/artifact-retention.md)保留。
